## 2026-10-20 GVCF and structural-record routing boundary

- **Production decision path:** after source artifact retrieval, `run_variant_analysis` profiles then partitions records with `route_vcf_records` before reference lookup. Sequence-resolved SNVs/indels (including a GVCF concrete ALT only when every sample has a complete genotype that does not call `<NON_REF>`/`<*>`) proceed to the pinned reference package and `normalize_vcf_with_bcftools`. Pure GVCF reference blocks, wildcard-called or unresolved GVCF variants, symbolic SVs, breakends, and `*` spanning-deletion records are persisted as separate deterministic review artifacts with source artifact id/hash, routing version, record count and `NOT_ANALYZED` state. If no sequence variant remains, normalization becomes `REQUIRES_REVIEW`, rather than claiming successful analysis or labeling a valid but unsupported record malformed. If mixed input has sequence variants, those variants may proceed, while report eligibility prevents signout until all preserved records have been interpreted. Annotation can subsequently block independently when its provider is unavailable.
- **Scientific/tool basis:** VCF v4.3 describes gVCF reference-confidence blocks using `<*>`/`<NON_REF>` and `END`, and breakends use mate/orientation representation ([official VCF specifications](https://samtools.github.io/hts-specs/VCFv4.3.pdf)). BCFtools 1.19 release notes describe `bcftools view -A` as removing unseen alleles such as `<*>`/`<NON_REF>` at variant sites, while `bcftools norm` handles reference-aware sequence normalization; these operations do not themselves interpret reference blocks or provide a complete SV workflow ([official BCFtools release notes](https://github.com/samtools/bcftools/blob/develop/NEWS), [BCFtools manual](https://samtools.github.io/bcftools/bcftools)). Therefore the code uses `view -A` only for wildcard alleles proven uncalled from complete sample GTs and preserves reference blocks and SV representations for a future appropriate workflow. No assembly conversion or SV interpretation is performed.

### PostgreSQL CI follow-up — concurrent VCF case lock mode (2026-10-19)

- **Observed evidence:** PostgreSQL integration first failed on `4f05f3b` in [run #392298](https://github.com/SayedaRehmat/SIRALOOM/actions/runs/39229846552); it failed again on `72f30a9` in [run #392307](https://github.com/SayedaRehmat/SIRALOOM/actions/runs/39230702456) and on ledger-only `36cb73a` in [run #392310](https://github.com/SayedaRehmat/SIRALOOM/actions/runs/39231005975). - **Root-cause analysis:** the new PostgreSQL concurrency test inserts child `Artifact` rows before locking the parent `Case`. PostgreSQL foreign-key checks hold KEY SHARE locks on the parent; two upload transactions then requesting `FOR UPDATE` can deadlock while upgrading their locks. This is consistent with the first failure appearing in the commit that introduced this test and with the repeated PostgreSQL-only failure. SQLAlchemy documents `key_share=True` as PostgreSQL `FOR NO KEY UPDATE`, which remains a writer-serializing row lock while being compatible with KEY SHARE.
- **Correction verified:** the case readiness recomputation uses `with_for_update(key_share=True)`. This emits PostgreSQL `FOR NO KEY UPDATE`, serializing competing readiness writers while remaining compatible with the artifact foreign-key KEY SHARE lock ([SQLAlchemy documentation](https://docs.sqlalchemy.org/en/20/core/selectable.html#sqlalchemy.sql.expression.GenerativeSelect.with_for_update)). The concurrent valid/invalid VCF regression passed in exact-main CI.
