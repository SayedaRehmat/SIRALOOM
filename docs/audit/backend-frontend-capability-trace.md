# Backend-to-frontend capability trace — release qualification

**Repository baseline reviewed:** `main` at `52e41346df0c2879ce8c80c32f31936389130783` (2026-10-12).  
**Purpose:** distinguish code presence, UI integration, and validated behavior. This is a source review, not a live deployment test.

## Status vocabulary

- **SOURCE PRESENT:** backend and/or frontend code exists.
- **UI WIRED:** a frontend route calls the corresponding API.
- **GAP:** missing user-facing management or a contract mismatch was found.
- **NOT LIVE-VALIDATED:** deployed behavior, permissions, and real persistence have not been verified in a controlled tenant.

## Important storage and upload facts

- The API's documented default `MAX_ARTIFACT_UPLOAD_BYTES` is **512 MiB**.
- The deployment guide explicitly warns not to raise it to 5–10 GiB before measuring ingress, multipart spooling, temporary storage, artifact storage, scratch space, timeouts and concurrent uploads.
- Capacity preflight estimates artifact and scratch demand using configured multipliers/headroom. It reports `reservation_supported: false`; another job can consume space after preflight.
- The lab deployment must bind the API and worker to the same persistent artifact and scratch roots, and separately configure PostgreSQL, Redis, reference data, resource cache and backups.
- Never advertise arbitrary multi-gigabyte VCF support until the exact deployed path has passed large-file, concurrency, worker-restart and disk-exhaustion tests.

## Release validation still required

1. Run backend/frontend CI on the exact merge candidate and inspect logs, not just the deployment badge.
2. In a dedicated non-production organization, exercise case creation through report/provenance download with a public benchmark VCF and a real configured reference/provider.
3. Inject worker loss at the start of and during every durable stage; compare persisted rows, artifacts, partition/checkpoint state and output hashes before/after recovery.
4. Test human review, phenotype, pedigree, segregation, inheritance, QC, reportability, sign-out and resume with authorized and unauthorized roles.
5. Test cross-tenant access denial for case, artifact, export, report, notification and resource APIs.
6. Measure 512 MiB first, then progressively larger files; only claim 5–10 GiB after recording measured upload success, peak temporary/persistent/scratch usage, elapsed time and concurrent workload behavior.
7. Compare scientific output against a defined truth set and record precision/recall/concordance under a versioned validation protocol.

**No row in this source map should be treated as a live deployment pass without execution evidence.**


## UX design basis reviewed

The public and authenticated surfaces should follow these principles:

1. **Case-first navigation:** a case list/worklist is the entry point; case identity, specimen/input artifacts, analyses, review tasks, reports and audit history remain connected.
2. **Evidence before conclusion:** present source, version, direction and rationale alongside evidence; distinguish automated assessment from reviewer decision and reportability.
3. **Explicit workflow state:** show the current step, completed work, blockers, retry/recovery state, responsible action and audit history. A status badge must not substitute for the underlying evidence.
4. **Role-appropriate actions:** expose decisions only to authorized roles; show actionable error states rather than silently hiding failed operations.
5. **Readable data density:** compact page headings, predictable tables, restrained borders, consistent spacing, keyboard focus, responsive layouts and text labels in addition to color.
6. **No false clinical claims:** mark illustrative examples as synthetic; do not imply that a software workflow or automated ACMG result is a clinically validated diagnostic conclusion.
7. **Language consistency:** public and authenticated navigation must expose the same language choices; Arabic requires RTL testing, and bilingual mode must render both languages rather than silently falling back to English.

These principles are informed by the [ClinGen Variant Curation Interface paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC8764818/), the [ACMG/AMP variant-classification consensus recommendations](https://pmc.ncbi.nlm.nih.gov/articles/PMC4544753/), the [ACMG points-to-consider statement on genomic data in the health record](https://www.nature.com/articles/s41436-020-0841-2), and a [WHO-published usability evaluation of a laboratory information system](https://www.emro.who.int/emhj-volume-26-2020/volume-26-issue-12/compliance-with-design-principles-a-case-study-of-a-widely-used-laboratory-information-system.html). These references inform interface design; they do not validate SIRALOOM itself.
